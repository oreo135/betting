## Что это
Парсер статистики HLTV — поставщик данных для сервиса прогнозов CS2.
Трёхслойная архитектура: raw store (файлы data/raw/ + таблица raw_pages, сеть ТОЛЬКО тут)
→ parse (только из файлов) → records (таблицы БД cs_analytics.db).

## Железные границы (нарушение = провал)
- Транспорт src/browser_client.py (DrissionPage/CF) НЕ трогать по существу.
  CF проходит, clearance переживает перезапуск — выстраданный актив.
- Парсеры читают из raw store (файлов), НЕ из живого page.html.
- Новые данные парсить ОФЛАЙН на фикстурах корпуса, где возможно.
- Не кодить сверх поставленной задачи. Не рефакторить ради красоты. Не менять сигнатуры без нужды.
- НЕ переносить/не реструктурировать проект — чистый перенос будет отдельной задачей ПОСЛЕ E6.
- Держать tests/ зелёными. Запуск — `venv/bin/python tests/run_all.py`: он же
  СТЕРЕЖЁТ БОЕВЫЕ БАЗЫ (факты, журнал движка, пред-матчевый стор) и падает,
  если прогон их изменил. Повод не теоретический: тест уже однажды дописал
  строки в боевой журнал, потому что подменял базу фактов, а движок берёт путь
  к своей базе из окружения.

## Сеть и анонимность
- HLTV — данные ПУБЛИЧНЫЕ, логина нет → идти НАПРЯМУЮ, анонимность НЕ требуется.
  (Tor ломает CF на HLTV. Анонимность — только для бука в cs_service.)
- Лайв-сокет (scorebot) — тот же HLTV, то же правило: напрямую, но за CF →
  cf_clearance + согласованный UA из browser_client. Подробности — _context/LIVE_SOCKET.md.
- Вежливость: паузы в коде НЕ менять, не массовый сбор, СТОП при первом CF-челлендже.
