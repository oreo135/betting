**Модель на игрока с N картами** (паузы из кода: 3 с после каждой некэшированной L3 и после каждого L2):

- с L2: запросов `= N + 7`, время `≈ 27 + 4.5·N` с
- `skip_l2=True`: запросов `= N + 2`, время `≈ 4.4 + 4.5·N` с
- кэш `match_maps`: повторная L3 = **0 запросов и 0 пауз** (повторные прогоны резко дешевле)

**Экстраполяция на 10 игроков:**

| N карт | Запросов (с L2) | Время (с L2) | Запросов (skip_l2) | Время (skip_l2) |
|---|---|---|---|---|
| 10 | 170 | ~12 мин | 120 | ~8 мин |
| 20 | 270 | ~19.5 мин | 220 | ~16 мин |
| 30 | 370 | ~27 мин | 320 | ~23 мин |
| 50 | 570 | ~42 мин | 520 | ~38 мин |

**Рекомендованный максимум N: 30 карт на игрока** (= 370 запросов / ~27 мин на 10 игроков).
Обоснование: это текущий дефолт `--n-matches 30`, он укладывается в получасовое окно,
и при нём не нужна пагинация. Комфортный рабочий режим — **N=20** (~270 запросов / ~20 мин).

**Жёсткий потолок сверху: N ≤ 100.** L1 отдаёт ровно одну страницу — 100 строк
(у s1mple в карьере 1914 карт, распарсилось 100). Пагинации в `get_match_list` нет,
больше 100 карт на игрока текущим кодом не достать.

## 5. Вердикт — что чинить, по приоритету

Только реально сломанное, в порядке убывания важности.

**1. [КРИТИЧНО] `matches.build_player_record` сопоставляет CT/T-строки по индексу — данные едут.**
`ct_list[i]` / `t_list[i]` предполагают одинаковый порядок игроков в таблицах overall/ct/t.
Факт: HLTV сортирует **каждую сторону по её собственному рейтингу**. На проверенной карте:
```
FOKUS   overall [Matheos, Banjo, ztr, podi, jocab]
FOKUS   ct      [podi, jocab, ztr, Matheos, Banjo]   ← 4 из 5 позиций разъехались
BC.Game t       [s1mple, Magisk, electroNic, Senzu, mzinho]  vs overall [s1mple, electroNic, Senzu, Magisk, mzinho]
```
Последствия (посчитано на живых данных):
```
s1mple      rating_t=1.48  (истина 1.48)  ok   ← совпало только потому, что он топ-1
Magisk      rating_t=1.23  (истина 1.39)  WRONG
electroNic  rating_t=1.39  (истина 1.35)  WRONG
Senzu       rating_t=1.35  (истина 1.23)  WRONG
```
То есть `rating_ct/adr_ct/kast_ct/rating_t/adr_t/kast_t` в `player_records` (311 строк в БД)
верны фактически только для топ-рейтингового игрока карты. Чинить сопоставлением **по нику**,
не по индексу. Таблица `map_player_stats` этим не затронута — там side пишется явно.

**2. [ВЫСОКИЙ] Live: счёт живой карты не собирается.** `_extract_scores` упирается в `"-"`.
Брать `.ctScore` / `.tScore` (плюс доступны номер раунда и таймер). Без этого live-модуль
не даёт основного in-play сигнала.

**3. [ВЫСОКИЙ] Live: `map_*` поля приписывают игроку статистику завершённой карты.**
Индексация `live_map_idx*2` неверна в принципе: контейнеры — `all-content` и
`{map_stat_id}-content`, и для живой карты totalstats-таблицы **нет**. Нужно либо выбирать
контейнер по `map_stat_id`, либо честно возвращать `None` для живой карты.
Заодно поправить контракт `sb_*`: это текущая карта, а не весь матч.

**4. [СРЕДНИЙ] `player._parse_info`: `country` и `photo_url` всегда `None`.**
`img[itemprop="nationality"]` больше не существует → читать `img.flag[title]`;
`bodyshot-img` → `player-summary-stat-box-left-bodyshot` (или `img[itemprop="image"]`).

**5. [СРЕДНИЙ] `flash_assists` содержит обычные ассисты.** Колонка `"A (f)"` = assists (flash).
Либо переименовать поле, либо доставать число из скобок.

**6. [НИЗКИЙ] `round_swing` из overview не использовать** — HLTV отдаёт `"-"` на all-time срезе.
Swing есть на L3 (`+4.44%`). Это не баг кода, а нерабочий источник.

**7. [НИЗКИЙ] Мёртвый груз и недобор.** `kast2/ekast2` — smartphone-дубликаты, можно выкинуть.
`_parse_category_cards` теряет 80 CT/T-строк ролей — если сплиты нужны, они уже в DOM.

**8. [НИЗКИЙ / инфраструктура]** `matplotlib` добавить в `requirements.txt`.
Хардкод путей Chromium **сегодня не мешает** (оба каталога на месте), но остаётся миной
на любой машине без `chromium-1228/1223`.

**Что НЕ сломано и трогать не надо:** транспорт DrissionPage (CF прошёл, clearance
переживает перезапуск), L1, L3 и его индексный маппинг, overview (кроме round_swing),
form-график, events-цепочка турнир→команды→ростер, `/search`, `/player/` как транспорт,
