# COVERAGE.md — разведка охвата HLTV

**Дата:** 2026-09-10
**Задача:** найти и задокументировать источники, которых парсер НЕ берёт, с прицелом
на 4 приоритетных пробела из STATE. Разведка, не сбор.

**Стоимость разведки: 7 навигаций.** Всё остальное — анализ уже сохранённого корпуса
(0 запросов). CF-челленджа не было ни разу: clearance из профиля Chromium переиспользуется
(см. REALITY.md). Все 7 новых страниц легли в raw store и сразу стали фикстурами.

Транспорт везде один и тот же — существующий `browser_client` (DrissionPage).
**Отдельных JSON/XHR-эндпоинтов у HLTV для этих данных нет** — всё приходит в HTML,
часть как inline-JSON в `data-*` атрибутах (тот же приём, что form-график в overview).

## 2. По каждому приоритетному пробелу

### #1 Round-by-round — **ЗАКРЫТ** (главный результат)

**Да, публичная пораундовая последовательность на HLTV существует. Демки для этого не нужны.**
Закрывают две страницы, дополняя друг друга:

`economy` даёт по каждому из 24 регулярных раундов: сторону, категорию закупа,
**точную стоимость снаряжения**, и кто раунд проиграл. Пример из фикстуры (237040, Nuke):

```
rd half | BC.Game           equip  res | FOKUS             equip  res
  1    1 | ctPistolLoss       4200 LOSS | tPistolWin         4450  WIN
  2    1 | ctForcebuyLoss     9200 LOSS | tRifleArmorWin    20550  WIN
  5    1 | ctRifleArmorWin   26500  WIN | tRifleArmorLoss   24800 LOSS
 13    2 | tPistolWin         4250  WIN | ctPistolLoss       4000 LOSS
 14    2 | tRifleArmorLoss   20600 LOSS | ctForcebuyWin     11550  WIN
```
Проверка целостности: ровно один победитель в каждом раунде, сумма 12–12 = регламент.

`performance` даёт **событийную последовательность внутри раунда** с собственной
моделью вероятности HLTV: `y` — вероятность победы в раунде после каждого события
(`buy → kill → kill → … → bombplant → bomb_exploded`), `tooltipId` привязывает событие
к player_id + номеру раунда + индексу события. Плюс **причина конца** каждого раунда
(взрыв / разминирование / элиминация / время) и текущий счёт после раунда.

**Чего всё равно нет:** имён «кто кого убил» в точках графика (только иконки типов
событий и привязка к игроку-владельцу графика), таймингов внутри раунда в секундах,
координат (это на `heatmap`), и **overtime в `economy`** — сетка обрывается на 24
регулярных раундах, хотя карта закончилась 16–19. `performance` при этом покрывает
все 35 раундов. Для полной OT-экономики этого источника не хватает.

### #2 Расписание события — **ЗАКРЫТ** (но не там, где ожидалось)

Рабочий источник — **`/matches`**, а не `/events/{id}`. Один запрос отдаёт 423 будущих
матча на 23 дня по 22 турнирам, с `data-event-id`, точным `data-unix` и `bo`.
Турнир-центричный вход делается фильтром по `data-event-id` **после одного запроса**.

**Важно:** `?event={id}` в URL **не применяется на сервере** — `/matches?event=8050`
вернул тот же полный список (425 карточек, ни одной с `data-event-id=8050`);
фильтрация на сайте клиентская. Так что «одна страница + фильтр в памяти», а не
запрос на турнир. Для match-centric это даже дешевле.

`/events/{id}` расписания не содержит (по крайней мере для события, которое ещё не
началось) — только мету и участников.

### #3 Командный уровень — **ЗАКРЫТ в основном**

`/stats/teams/maps/{id}/{slug}` закрывает map winrate и стату по картам, включая
`Pick %` / `Ban %` и конверсию первого килла в раунд. `/stats/teams/{id}/{slug}` —
агрегаты команды. **H2H команд** есть на странице матча (`.head-to-head`: wins +
overtimes по каждой стороне, плюс `.past-matches`).

Не проверял: вкладки `/stats/teams/matches|players|events/{id}` (6 пунктов меню) —
по ним не ходил, чтобы не долбить.

### #4 Вето / map pick-ban — **ЗАКРЫТ, ценой 0 запросов**

`.veto-box` на странице матча отдаёт полную упорядоченную последовательность
pick/ban с названием команды на каждом шаге и «was left over» для решающей карты,
плюс формат серии и стадию сетки. Фикстура **уже была в корпусе** (`live`, матч 2397733).

**Ограничение по природе данных:** вето появляется только после того, как оно
состоялось (обычно незадолго до матча). Как чистый предматч-сигнал «заранее» оно
недоступно; зато `Pick %` / `Ban %` из `team_maps` — это его априорная замена,
доступная в любой момент.

## 4. Вывод: что включить в контракт match-package

По соотношению ценность/цена:

1. **`/matches` один раз за цикл** — корень match-centric воркфлоу: match_id, event_id,
   unix-старт, bo, команды, звёздность. Фильтрация по турниру в памяти. Дёшево (1.4 MB, 1.5 с).
2. **Страница матча** (`/matches/{id}/{slug}`) — на матч: вето, H2H, lineups, формат,
   стадия. Уже достижима, уже в корпусе, CF не требует.
3. **`economy` на карту** — пораундовая экономика + последовательность побед раундов.
   351 KB и 2.7 с за карту: это основной кандидат в пакет для калибровки δ.
4. **`team_maps` на команду** — map winrate, Pick%/Ban%, конверсия первого килла.
   Предматчевый приор, 378 KB на команду, кэшируется надолго.
5. **`performance` — выборочно**, не в базовый пакет: 8.9 MB на карту НА ДИСКЕ.
   Уточнение (2026-09-16): по сети это **0.4 MB gzip**, то есть обычная страница —
   тяжесть тут в хранении и парсе, не в трафике; regex-разбор 0.1 с, DOM не нужен.
   Брать под конкретную задачу (событийная кривая вероятности, причины конца
   раундов, OT), когда пораундовой экономики недостаточно, И под «чистоту раунда»
   (выжившие) — единственный источник, см. SURVIVORS.md.

Осознанно вне пакета: `heatmap` (позиции, к задаче не относится),
вкладки игрока (`career/individual/opponents/weapon`) — потенциально полезны для prior,
но это отдельная разведка.

**Границы соблюдены:** парсеры под находки не писались, records-схема не менялась,
данные впрок не собирались, отложенные баги не чинились. Единственное изменение кода —
расширение списка `SOURCES` в `raw_store.py` под новые теги фикстур.
